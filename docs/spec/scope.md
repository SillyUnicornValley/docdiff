# 目标、范围与部署

> 现行规则。改动时直接改本文件，并在 [../decisions.md](../decisions.md) 记一条决定。
> 支持哪些文件见 [reading.md](reading.md) §1；每种 Word 元素的逐项状态见 [comparison.md](comparison.md) §8。

## 1. 产品目标

做一个在公司 Windows 浏览器中使用、无需安装客户端的 Word 文档对比与合并工具。

用户可以像阅读 VS Code 的左右 diff 一样，查看旧版与新版的对应内容和差异。对每一处差异，选择采用旧版还是新版，最后导出合并后的 Word 文件。

第一阶段聚焦英文 Word 文档的主体内容，包括正文和表格。内容检查与格式检查分开，优先实现内容比较。Excel 后续再考虑。

## 2. 已确认需求与设计理由

| 需求 | 具体约定 | 为什么这样做 | 详见 |
|---|---|---|---|
| 使用环境 | 公司 Windows 浏览器；无需安装客户端 | 方便在工作环境中使用，减少安装与分发负担 | §3 |
| 界面语言 | 英文 | 与文档语言一致，便于不懂中文的同事使用 | |
| 使用方式 | 首版为个人使用；不设计多人协作或审阅交接 | 先满足个人审阅场景 | |
| 文档规模 | 十几页到 200 页以上；目前没有处理时间要求，但长文档需显示处理进度、界面不卡顿 | 覆盖实际文档范围 | |
| 部署形态 | 文件只在用户浏览器本地处理，不上传服务器；可发布到 Posit Connect，也可作为单个 HTML 文件离线使用 | 文件不离开本机，合规风险最小；同一套产物两种用法 | §3 |
| Word 优先 | 先支持英文 .docx，包含表格；.doc 不支持；Excel 后续开发 | 聚焦主要使用场景，先保证一种文档的比较与合并可靠 | |
| 左右对比 | 左边旧版，右边新版；对应内容对齐 | 直观看清修改前后内容，减少来回查找 | [ui.md](ui.md) |
| 统一阅读样式 | 两边使用同一套阅读样式，保留标题层级、列表、表格等结构 | 保持可读性，同时减少原始格式差异对内容审阅的干扰 | [ui.md](ui.md) §1 |
| 内容与格式分开 | 分别检查、分别呈现；先实现主体内容比较 | 避免字体、间距等变化淹没内容修改 | [comparison.md](comparison.md) §1 |
| 已有修订 | 两份上传文档均按接受全部已有 Track Changes 后的状态参与比较 | 为每份文件取得明确的内容状态 | [reading.md](reading.md) |
| 原文件不变 | 在内部工作副本上处理，不修改上传的原文件 | 保留原始文件及其历史 | |
| 合并方式 | 每处差异选择“采用旧版”或“采用新版”，默认新版；任何选择组合都有效 | 与 VS Code diff 的使用习惯一致，选择之间不会互相冲突 | [merge.md](merge.md) |
| 导出底稿 | 以接受已有修订后的新版文件为底稿，只修改选择了旧版的位置 | 尽量保留新版的样式、结构和其他文档元素 | [export.md](export.md) |
| Clean 导出 | 优先开发；输出合并后的 Word，无未决修订 | 首先完成实际可用的工作闭环 | [export.md](export.md) |
| Track Changes 导出 | 后续开发；记录“新版 → 最终版”的变化；首版数据结构为此预留 | 让接收者查看本次审阅对新版做了哪些调整 | [export.md](export.md) §3 |
| 导出样式 | 保留新版原有样式体系；不将网页统一样式写回 Word | 网页用于清楚阅读，Word 保持正式文档样式 | [export.md](export.md) |
| 批注 | 不比较；Clean 保留新版已有批注，不汇入旧版批注；内容视图中显示新版批注的位置标记，只作提示 | 聚焦主体内容；选择前就能知道哪里挂着批注 | 决定 8、19 |
| 未比较可见 | 不支持比较的元素必须在界面上可见，并标为“未比较” | “未比较”不能被误读为“无差异” | [comparison.md](comparison.md) §5 |
| 工具内编辑文字 | 不支持；需要第三种写法时，导出后在 Word 中修改 | 首版聚焦二选一 | 决定 13 |
| 非“旧→新”场景 | 暂不支持（如两家供应商的合同对比），沿用 old / new 模型 | 先把“旧→新”做好 | 决定 20 |

## 3. 部署形态与技术方向

### 3.1 部署形态

- 所有解析、比较、合并、导出都在浏览器本地完成，文件不上传。
- 同一份构建产物有两种用法：
  - 作为静态网页发布到公司 Posit Connect；
  - 作为单个 `.html` 文件分发，离线双击使用。
- 页面显示版本号。以 Posit Connect 上的版本为准，离线副本需自行替换为最新版本。
- 不依赖大模型做基础差异检测。

为什么选纯浏览器端而不是服务器端，当时的对比分析见 [../archive/design-review-v0.1.md](../archive/design-review-v0.1.md) §1。

### 3.2 技术方向

- TypeScript + Vite + React。
- JSZip 读写 .docx；浏览器原生 `DOMParser`／`XMLSerializer` 操作 XML，未修改部分原样保留（决定 22）。
- 段落与表格行对齐使用自研算法：先按规范化文本序列对齐，再在变化区间内按相似度配对，处理改写、拆段、合段与移动。
- XML 解析和写回在主线程（`DOMParser` 不能在 Worker 中使用），对齐和比较在 Web Worker 中运行；长文档使用虚拟滚动；不使用 Monaco。
- 单文件构建，以支持离线使用。
- 自动化测试以 `testdocs/` 为黄金样例。

技术细节由开发方决定（决定 23），见 [../implementation/](../implementation/)。

### 3.3 需要在公司环境确认

- 公司 Edge／Chrome 能否从本地打开含脚本的 HTML 文件。
- 浏览器是否允许页面启动后台线程（Web Worker）。不允许时工具会自动退回普通方式运行，结果相同，只是很长的文档比较时界面可能短暂停顿。
- 通过邮件或 Teams 收到的 HTML 文件是否被拦截。
- Posit Connect 发布静态内容的权限。

## 4. 分阶段范围

| 阶段 | 交付重点 |
|---|---|
| 1. 界面原型 | 左右布局、统一阅读样式、正文与表格差异、选择与状态、最终结果预览、占位符与检查范围面板 |
| 2. 主体内容比较 | 解析 .docx、处理已有修订、段落和表格对齐、移动识别、词级差异 |
| 3. 合并与 Clean 导出 | 按选择修改新版、结构保护、撤销、审阅进度、导出与自检 |
| 4. Track Changes 导出 | 记录新版到最终版的变化 |
| 5. 扩展检查 | 格式检查、自动编号比较、未比较元素的逐项比较、带回含脚注等元素的旧版内容、段内词级选择、批注处理 |
| 6. Excel | 单独定义表格文件的匹配、展示及合并规则 |

各阶段的完成情况见 [../overview.md](../overview.md) §4。

### 4.1 第一阶段的比较范围：主体内容

- 正文和标题文字的新增、删除、修改。
- 列表文字和条目增删（不含自动编号本身，见 [comparison.md](comparison.md) §6）。
- 表格单元格文字修改；表格行增删；列和合并单元格的结构变化识别为“表格结构变化”。
- 段落及表格的对齐，包括改写、拆段、合段。
- 移动内容的识别。
- 上标、下标作为内容参与比较。
- 隐藏文字显示（虚线标注）并参与比较。
- 英文词级差异高亮。

### 4.2 以后的范围

- 格式差异：字体、字号、颜色、段落间距、样式、标题层级、列表类型、表格格式等。
- Track Changes 导出。
- 页眉页脚、脚注、尾注、文本框、超链接地址、图片等元素的专门比较，按需要逐步扩展。
- 批注比较，以及批注锚点受合并影响时的处理。
- Excel 对比，单独设计工作表、单元格和记录匹配逻辑。

## 5. 验收标准

逐条的完成状态和对应测试见 [../overview.md](../overview.md) §4.2。

1. 仅发生样式变化、文字未变时，内容比较不产生虚假的文字修改。
2. 同一段落因 run 拆分、换行或分页不同，不被误判为内容变化。
3. 新增一个段落后，后续相同内容仍能合理对齐。
4. 英文句子中仅一个词或数字变化时，能够清楚高亮实际修改；上下标中的变化同样能识别。
5. 表格保持表格呈现，能够识别单元格修改和行增删；结构变化时提供整表选择。
6. 上传文件已有修订时，比较结果基于接受全部修订后的内容。
7. 默认最终结果等于处理已有修订后的新版；全部采用新版时，导出内容与接受修订后的新版一致。
8. 选择与撤销仅改变选定片段。
9. 移动内容合成一个差异，任何选择都不产生重复或丢失。
10. 自动编号的顺延不被判为内容变化。
11. 采用旧版不破坏分节、页面设置、书签和批注结构；撤回含分节符的新增段落后，其余部分页面设置不变。
12. Clean 导出没有未决修订，保留新版已有批注与基础样式，并能被 Word 正常打开。
13. 后续 Track Changes 导出仅反映新版到最终版的差异。
14. 原始上传文件不变。
15. 未支持或未检查的内容有明确说明和占位，不被显示为“无差异”。
16. 审阅进度可保存并在同样两份文件上恢复。

## 6. 技术验证重点

- 段落增删、改写、拆段、合段、移动和重复内容能否合理匹配（testdocs 01、06、07、13）。
- 长文档的加载、比较与滚动性能（testdocs 07）。
- 表格行列增删、合并单元格、嵌套结构的处理（testdocs 03、10）。
- 列表和自动编号能否准确显示与保留（testdocs 02）。
- 已有修订是否正确接受，避免漏读或重复读取文字（testdocs 04、12）。
- 未比较元素的占位与指纹提示；分节符、书签等结构在合并后是否完好（testdocs 05、09）。
- 合并后的内容是否正确写回 Word；导出文件能否被 Word 正常打开，未涉及区域是否保持完整。
- 新版批注是否得到保留。
- 公司浏览器环境、离线 HTML、Posit Connect 部署是否可行。

这些是实现验证事项，不代表已决定额外功能。
