# Stage 2 技术方案：.docx 解析与比较引擎

2026-10-07。读写方案见 `design-review-v0.1.md` §5 第 22 条。其余技术细节由开发方决定，记录在本文；影响用户所见效果的问题单独列在 §7，需要用户决定。

Stage 2 只做“解析 + 比较”，输出原型已在使用的 `DiffResult`（`src/model/diff.ts`）。导出 Word 属于 Stage 3，本文 §5 先定下原则，避免 Stage 2 的结构以后要返工。

## 1. 整体流程

```
文件 → JSZip 解压 → DOMParser 解析 XML（主线程）
     → 在 XML 副本上“接受全部已有修订”
     → 读取为 DocModel（纯数据）+ 源位置表（只留在主线程）
     → DocModel 发给 Worker → 对齐 + 词级比较 → DiffResult
     → 界面（沿用原型）
```

- 两份文件都走同一套读取流程。
- 源位置表记录“每个段落、表格行、单元格，以及段落中每段文字，对应 XML 里的哪个节点、哪个位置”。XML 节点不能发给 Worker，所以它只留在主线程，导出时使用。
- 新增依赖只有两个：`jszip`（解压和打包）和 `diff`（jsdiff，词级比较）。都打进单文件，不需要联网。

## 2. 读取规则（XML → DocModel）

沿用原型的 `DocModel`（`src/model/document.ts`），它本来就是按真实 Word 结构设计的。

| Word 内容 | 读取为 |
|---|---|
| `w:p` 段落 | `ParagraphBlock`；按样式判断标题级别（顺着 `basedOn` 链查 `outlineLvl`），有 `numPr` 的是列表项 |
| `w:t` 文字、`w:tab`、`w:br`（软回车） | 文字、`\t`、`\n` |
| 上标、下标、隐藏文字 | 保留为标记，参与比较（决定 4、11） |
| 加粗、字体、颜色等 | 丢弃，不参与比较 |
| `w:hyperlink` | 显示文字参与比较；网址只记指纹 |
| 域（`fldChar` 或 `fldSimple`） | 只读结果文字，记下域类型；TOC 域整体读成一个折叠的目录占位块 |
| 内容控件 `w:sdt` | 去掉外壳，照常读取里面的内容 |
| 脚注／尾注引用、图片、图表、文本框、公式、嵌入对象 | 占位符，只记指纹 |
| 书签、拼写标记、`lastRenderedPageBreak`、`proofErr` | 忽略，不产生任何字符（验收 2） |
| 新版批注 | 零宽度的位置标记（决定 19）；旧版批注不读 |
| 表格 | 行、单元格、`gridSpan`、`vMerge`；嵌套表格递归读取 |
| 自动编号 | 按 `numbering.xml` 计算出显示用的编号（如 “3.”、“a)”），只显示、不比较 |
| 页眉页脚、脚注正文、文档属性 | 只算指纹，供“检查范围”提示 |

“接受全部修订”在 XML 副本上执行，规则就是需求 §5 的读取规则：

- 删掉 `w:del`、`w:moveFrom` 和其中的内容；
- 去掉 `w:ins`、`w:moveTo` 的外壳，保留内容；
- 段落标记被删除时，把这段与下一段合并；
- 被删除的表格行整行删掉；
- 去掉 `*PrChange` 格式修订记录，直接采用当前格式；
- 遇到不认识的修订类型，记入“不支持的修订”，然后继续比较。

## 3. 对齐与比较

### 3.1 段落对齐（四步）

1. **先找“锚点”**：两边各自只出现一次的、文字完全相同的段落，按顺序配对（patience diff）。这样 06 中四个 “Not applicable.” 不会错配，因为它们夹在不同的标题锚点之间。
2. **锚点之间逐段比较**：在锚点之间的空隙里做标准的序列比较（Myers），找出相同、新增、删除的段落。
3. **在剩下的空隙里按相似度配对**：
   - 同一空隙里，旧版和新版的段落按顺序、按词的相似度配对。相似度不低于 0.5 的配成“修改”；低于 0.5 的分别算删除和新增。
   - 一段旧文与相邻几段新文拼起来高度相似（不低于 0.8），算“拆段”；反过来算“合段”。
4. **识别移动**：全文范围内，把剩下的“删除”和“新增”两两比较，相似度不低于 0.8 的配成“移动”。很短的段落（少于 5 个词）不认作移动，否则一句 “Not applicable.” 删了一处、加了一处，就会被误认为移动。

比较时用的段落文字就是 `flatten.ts` 规则得到的文字，界面高亮位置用的也是同一份文字。段落类型（标题级别、列表层级）不参与判断“是否相同”（需求 §4.2）。

### 3.2 表格

- 整张表在段落序列里算一个单位，用表格全部文字的相似度和其他单位配对。
- 配对的两张表如果列数相同、合并单元格结构兼容，就逐行对齐，算法与段落对齐相同，以“行”为单位；然后在配对的行里按列位置逐格比较。
- 列数变化或合并结构变化时，整张表算一个差异（决定 6、21）。
- 纵向合并单元格（`vMerge continue`）在比较时视为空格子。这样合并范围扩大一行只会影响那一行，不会打乱整张表的对齐（03 号 Lab 表）。
- 嵌套表格：单元格内容递归使用 §3.1 的方法。

### 3.3 词级差异

- 用 jsdiff 按“词 + 空白 + 标点”切分后比较。
- 如果一段里超过 60% 的词都变了，就不再拼凑零碎的词级高亮，整段显示为替换（06 中“整句完全改写”）。
- 每处词级改动单独判断是否只是空白、引号、短横线或大小写的变化，并标上对应类别，用于“按类别隐藏”（决定 9）。上下标变化不归入任何可隐藏类别（决定 4）。手打编号改为显示相同的自动编号，归入 “Numbering text” 类别（§7 U1）。
- 判断“采用旧版”能不能用：两侧任一侧含脚注、图片、超链接、域、文本框或嵌入对象时不可用（决定 15）。

### 3.4 性能目标

07 长文档（约 3600 段，含表格单元格）在普通办公电脑上，从选好文件到显示结果不超过 5 秒。比较在 Worker 中进行，界面显示进度，不会卡住。

## 4. 差异编号（DiffId）保持稳定

- 编号由内容计算得出：差异类型 + 旧文内容哈希 + 新文内容哈希 + 相同内容的出现序号。
- 引擎是确定性的：同样两份文件、同一引擎版本，编号一定相同。所以重新上传同样的文件后，保存的进度可以恢复。
- 引擎升级后，编号依然按内容计算。进度文件里内容对得上的选择照常恢复，对不上的提示“有 N 处选择无法恢复”。

## 5. 导出原则（Stage 3 实现，这里先定下）

- 以“已接受全部修订的新版 XML 副本”为底稿。只有用户选了“采用旧版”的地方才修改，从文档末尾往前改，前面的位置就不会因为修改而移动。
- 修改段落：保留新版段落属性；旧版文字继承新版相邻文字的格式，上下标随文字带回（需求 §7.6）。
- 带回已删除的段落：按 §7.6 的样式查找规则处理。
- 删去新增的段落：段内的分节符、书签和批注标记移到相邻保留的段落上。文档末尾的节设置始终跟随新版，避免 05 号文档出现“全文变横向”的问题。
- 在 `settings.xml` 中设置“打开时更新域”。
- 没有修改的部件（样式、图片、页眉页脚等）按原字节复制。
- 导出后重新读取导出的文件，与最终结果预览逐段核对，不一致时警告。
