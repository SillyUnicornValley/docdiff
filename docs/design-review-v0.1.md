# 需求 v0.1 设计审阅

- 日期：2026-10-07
- 对象：`Diff-Requirements.md` v0.1
- 目的：在动手前找出会在使用或实现中出问题的逻辑点，并列出需要决定的事项
- 配套：`testdocs/`，表格中 `05`、`06` 等编号指对应的测试文档

## 0. 结论速览

整体方向没有问题：

- 先接受全部已有修订，再比较，原文件不动；
- 内容与格式分开；
- 以新版 XML 为底稿做定点修改，而不是重新生成整份 Word。

这三条是正确、也是可实现的基础。

真正需要在动手前讲清楚的有五件事：

1. **合并模型**：改为“每处差异二选一（旧版／新版）”，并明确差异单元的粒度。见 §2、§3.1。
2. **采用旧版时带回什么**：只带文字，还是连同上标、脚注引用、图片、超链接、编号一起带回。这是“内容与格式分开”原则在实际操作中最容易出问题的地方。见 §3.3、§3.4。
3. **结构载体被误删**：分节符、目录、书签都挂在段落上，撤回一段新增内容可能连带删掉它们。最坏情况是全文页面方向改变。见 §3.5。
4. **“未比较”必须可见**：页眉、脚注内容、图片、超链接地址、隐藏文字等，内容视图里看不出来，用户会以为“没有差异”。见 §3.7。
5. **移动的内容**：普通 diff 会把它拆成“删除＋新增”两处。用户只处理其中一处，就会出现内容重复或丢失。见 §3.2。

## 1. 浏览器端是否合适

**结论：合适，推荐纯浏览器端。** 同一份构建产物可以有两种用法：部署到 Posit Connect 作为静态网页，或作为单个离线 HTML 文件分发。

| 对比项 | 纯浏览器端（推荐） | 服务器端（Posit Connect 上跑 Python） |
|---|---|---|
| 文件去向 | 文件不离开用户电脑，合规风险最小 | 文件上传到服务器，需评估数据管理要求 |
| 离线使用 | 可以：单个 `.html` 双击打开 | 不可以 |
| 部署与运维 | 静态文件，Connect 支持直接发布静态内容 | 需要 Python 运行环境、并发、会话、临时文件清理 |
| 解析与写回 .docx | JSZip 加浏览器自带 XML 解析器即可；两边本质都是直接操作 XML | python-docx 对修订、批注支持有限，同样要直接写 XML，没有明显优势 |
| 性能 | 3000 至 5000 段落在浏览器内比较完全可行；重计算放到 Web Worker | 不受客户端限制，但多一次上传、下载 |
| 局限 | 不能调用 Word 或 LibreOffice 做转换（例如 .doc、渲染校验） | 理论上可以装 LibreOffice，但公司服务器上未必允许 |

需要在公司环境验证的几点：

- 公司 Edge／Chrome 能否从本地 `file://` 打开含脚本的 HTML。
- 通过邮件或 Teams 收到的 `.html` 是否会被“网络来源标记”拦截。
- Posit Connect 上发布静态内容的权限。

建议的技术框架（我来定，讨论结束前不锁死）：

- **TypeScript + Vite + React**：类型约束对处理 OOXML 这类复杂结构很重要；React 生态最大，以后便于他人维护。
- **JSZip**：读写 .docx 压缩包。
- **原生 `DOMParser`/`XMLSerializer`**：操作 XML，保证未修改部分原样保留。
- **对齐算法自写**：段落和表格行先用规范化文本的哈希做序列对齐（patience/histogram 思路），再在变化区间内按相似度配对，处理拆段、合段、改写。词级差异用 `diff`（jsdiff）。
- **Web Worker**：运行解析和比较，避免界面卡顿。
- **长列表虚拟滚动**：不需要 Monaco。
- **单文件构建**：用 `vite-plugin-singlefile` 打成一个离线 HTML。
- **Vitest**：以 `testdocs/` 为黄金样例做自动化测试。

## 2. 合并模型的修正

你指出的“恢复旧版”表述不准确，我同意。更准确的模型如下。

**比较结果**是一串互不重叠的片段，每个片段要么“相同”，要么“差异”。一个差异片段 = 旧版里的一段连续内容（可以为空）对应新版里的一段连续内容（可以为空）。

| 差异类型 | 旧版一侧 | 新版一侧 | 选“旧版” | 选“新版” |
|---|---|---|---|---|
| 修改 | 有 | 有 | 用旧版文字 | 用新版文字 |
| 新增 | 空 | 有 | 不出现 | 出现 |
| 删除 | 有 | 空 | 出现 | 不出现 |

用户对每个差异片段做选择：**采用旧版** 或 **采用新版**。

**最终结果 = 依次拼接每个片段的取值**：相同片段原样保留，差异片段按选择取旧版或新版。

这个模型有一个重要性质：因为片段互不重叠且有固定顺序，**任何选择组合都是合法的**，不存在“这处选了旧版，那处就不能选新版”的冲突。VS Code 的 diff 和 merge 编辑器正是这样工作的。

“以新版为基础”在这个模型里只体现在两点，不再是交互上的主导概念：

- 默认值是“采用新版”；
- 导出时以新版文件为底稿修改 XML。

建议的配套规则：

- **三种状态**：未处理（默认按新版计算）、已采用新版、已采用旧版。界面显示“已处理 12／40”，可跳到“下一处未处理”。导出时有未处理项，不阻止导出，但给出提示。【待定】
- **左右两栏始终显示原始旧版和原始新版**，不随选择变化。被放弃的一侧淡化显示，片段上标明“已采用旧版／新版”。这样差异永远可以定位、可以改主意，满足需求 §6.3 的“仍可定位”要求。
- **另设“最终结果预览”**：切换视图或第三栏，让用户看到拼接后的完整文本。否则选了旧版之后，用户在界面上看不到最终长什么样。【待定】
- **批量操作**：本节全部采用旧版或新版；全部未处理项采用新版。
- **撤销／重做**：作用于选择记录，不作用于文档。
- **不支持自由编辑文字**（VS Code 允许）。如需第三种写法，导出后在 Word 里改。建议首版明确不做。【待确认】

## 3. 逻辑问题清单

### 3.1 差异片段的粒度

VS Code 以“行”为单位，一个连续的变化行块是一个可撤回单元，行内只做高亮。对应到 Word：**段落（以及表格行）就是“行”**。

问题在于：一段里有三处词级变化时，是整段二选一，还是三处分别选？

- **只做段落级**：实现简单、导出稳妥。缺点是同一段里“12→24 要旧版，其他要新版”做不到。
- **段落级＋段内词级子选择**：更灵活。代价是导出时要在新版 run 中拆分、插入旧词，旧词的格式需要从相邻的新版 run 继承。

建议首版做段落级，并预留词级子选择的数据结构，作为下一步增强。【待定】

另外两个与粒度相关的问题：

- **片段边界由对齐算法决定。** 对齐错了，片段就会把不相干的段落绑在一起，用户无法拆开。首版可以不提供“手动配对”，但要用测试文档 06 把算法调到可接受的程度。
- **拆段与合段（06、04 的 Washout）**：一对二或二对一是一个片段。选旧版就是回到旧的分段方式。词级高亮要能跨越段落分隔符显示。

### 3.2 移动的内容

普通序列对齐会把移动显示成“某处删除＋另一处新增”。如果用户只把其中一处选成旧版：

- “删除”处选旧版、“新增”处保持新版：内容出现**两次**；
- “新增”处选旧版、“删除”处保持新版：内容**消失**。

建议：

- 检测移动：完全相同或高度相似的“删除＋新增”配对。
- 两处显示为相互链接的一对，标“已移动”。
- 两处的选择联动：选旧版就放回原位置，选新版就留在新位置。

首版至少做到识别和提示，不能静默产生重复或丢失。测试文档 02、04、06、07 都有移动。【待定】

### 3.3 “采用旧版”时，哪些属性随文字一起回来

需求说内容与格式分开、恢复一个词不应带入旧版整段格式，原则正确。但有些格式本身承载内容。

| 属性 | 建议归类 | 理由 |
|---|---|---|
| 上标、下标 | **内容**：参与比较，采用旧版时随文字带回 | `10⁶` 和 `106` 意思完全不同（06） |
| 加粗、斜体、下划线、颜色、字体、字号 | 格式：不参与内容比较 | 带回时继承新版相邻文字的格式 |
| 删除线（非修订） | 待定 | 少数文档用它表达“作废” |
| 标题层级 | 结构：不参与内容比较 | 但**整段带回**旧版标题时，必须保持它是标题 |
| 列表成员、列表层级 | 结构 | 整段带回旧版列表项时，要挂到新版相应列表上 |

由此引出一条必须定下的规则：

- **修改类片段**：保留新版段落的样式和编号，只替换文字。
- **删除类片段带回**（新版里已经没有这段）：需要为它决定样式。

建议做法：

- 按样式名称在新版中找同名样式，找不到就用旧版样式的大纲级别对应新版的标题样式，再不行用正文。
- 列表项挂到新版中位置相邻的同层级列表；没有的话，在新版 numbering 中新建一个。
- 直接格式不带回。

### 3.4 带回旧版内容时，附带的非文本元素

旧版段落里可能含脚注引用、图片、超链接、域、书签、批注锚点。它们引用的是**旧版文件里的** ID，例如脚注编号、关系 ID `rId`、编号 ID `numId`，这些在新版文件中不存在。如果直接复制 XML：

- 轻则引用失效；
- 重则 Word 打开时报“文件已损坏”。

建议首版规则：

- 片段只含普通文字、上下标、制表符、软回车：可以采用旧版。
- 片段含首版不支持迁移的元素（脚注、图片、域、超链接）：
  - 仍显示差异；
  - “采用旧版”按钮置灰，并说明原因：“此处含脚注，首版暂不支持带回，请导出后在 Word 中处理”。
  - 以后再逐步支持迁移：复制脚注内容、图片和关系，并重新编号。

这条规则宁可保守，也不能导出一个打不开的文件。【待定】

### 3.5 结构载体被误删（关键）

有些文档级结构挂在普通段落上：

- **分节符**：`sectPr` 写在一节最后一个段落的属性里。测试文档 05 中，新版在 `End of main protocol.` 这个新增段落上挂了分节符，后面跟横向附录，而文档最后一节就是这个横向节。
  - 如果用户把附录和这一段都选回旧版（即删掉），分节符随段落消失。
  - 文档末尾的节属性仍然是新版的“横向”，结果**整份文档变成横向**。
- **书签**：交叉引用的目标可能落在被替换的文字里，书签丢失后引用会显示“错误！未找到引用源”。
- **批注锚点**：见 §3.8。
- **目录、域的开始和结束标记**：分布在不同段落，删掉其中一段会破坏域结构。

建议规则：**撤回或替换段落时，结构标记不随文字删除。**

- 分节属性转移到相邻保留下来的段落。
- 书签起止点收缩到相邻位置。
- 域边界如果跨越片段，该片段不允许采用旧版，并说明原因。

文档末尾的节属性始终跟随新版。这条规则需要专门测试。

### 3.6 表格

| 变化 | 建议首版能力 |
|---|---|
| 单元格文字修改 | 单元格级二选一 |
| 行新增或删除（无合并单元格跨越） | 行级二选一 |
| 列新增或删除、合并单元格结构变化、表格嵌套结构变化 | **整表二选一**，并说明“表格结构变化，首版只能整表选择” |
| 段落与表格互换（03） | 整块二选一 |

这样处理的原因：

- 列和合并单元格的局部恢复，牵涉每一行的单元格、列宽（`tblGrid`）和合并跨度，任一处不一致，Word 就会把表格显示坏。
- 整表选择不会产生坏文件，且以后可以细化。

另有两点：

- **行对齐**：按行内容相似度配对，而不是按行号。
- **表头行**：如果表格跨页重复表头，内容只算一次。

### 3.7 “未比较”必须看得见

内容视图看不出以下差异，用户会误以为两边一致：

- 页眉、页脚
- 脚注、尾注的内容
- 图片
- 超链接的地址
- 文本框
- 隐藏文字
- 嵌入对象
- 文档属性

建议：

- 内容视图中，凡是首版不比较的元素，都用占位符显示，例如 `[图片 · 未比较]`、`[脚注 2 · 内容未比较]`，让人知道这里有东西。
- 顶部常驻“检查范围”面板，列出已比较的元素和未比较的元素（附各自数量），以及“格式：未检查”。
- 对未比较元素做一次**廉价的指纹对比**：只判断“相同”或“可能不同”，不展示具体差异。例如页眉文字不同时提示“页眉存在差异，未逐项比较”。这样成本很低，但能避免“未比较≈无差异”的误解。【建议】

超链接地址：显示文字相同、地址不同时，首版建议用上面的指纹提示。

隐藏文字：建议显示（虚线标注）并参与比较，因为它在 Word 里一切换就能看到。【待定】

### 3.8 批注

需求要求 Clean 导出保留新版已有批注。但批注锚点可能落在会被替换或删除的新版文字上（05）：

| 情况 | 建议处理 |
|---|---|
| 锚在未变化的内容上 | 原样保留 |
| 锚在某个修改片段内，且该片段选了旧版 | 保留批注，锚点收缩到替换后文字的首尾；片段上提示“此处有新版批注” |
| 锚在某段新增内容上，该新增被撤回 | 保留批注，锚点移到相邻位置，例如上一段末尾；导出前在汇总中列出这类“锚点已移动”的批注 |

无论哪种情况，都不静默删除批注。内容视图中最好显示新版批注的位置标记（只显示，不比较），让用户在选择前就知道会影响批注。

### 3.9 自动编号与目录

- **自动编号**（列表、标题编号）是 Word 渲染时算出来的，不是文字。
  - 显示时可以算出来给人看，但**比较时必须排除**，否则插入一条，后面所有条目都会被判为修改（02）。
  - 手打的编号（`1) …`）是文字。手打改自动时，会出现“`1) ` 被删除”的差异。首版可以接受，并在说明中写明。
- **目录（TOC 域）**的缓存文字会随标题变化。如果按普通文字比较，会产生大量噪声。
  - 建议识别目录区域，默认折叠，标“目录·未比较（导出后请在 Word 中更新域）”。
- **DATE、PAGE 等动态域**：建议同样只显示结果，标为域，不作为内容差异。【待定】

### 3.10 文本规范化

参考 VS Code 的“忽略空白”。以下差异建议**默认不报**，或归到可筛选的“仅空白／标点”类别：

- 多个空格与一个空格
- 不换行空格与普通空格
- 段首、段尾空格
- 空段落的增减

以下建议**默认报出**，但标记为“标点变化”，便于一键隐藏：

- 直引号与弯引号
- 连字符与 en dash、em dash
- 大小写变化

软回车（`Shift+Enter`）与空格之间的互换：建议当作空白差异。

需要你确认默认值。【待定】

### 3.11 已有修订

- **含义提醒**：新版中别人尚未接受的修订，会在导出后**被一并接受**，导出文件中不再有这些修订记录。这是需求已确认的规则，但对使用者影响大。建议在固定说明之外，在新版含未决修订时，于导出确认框中再提示一次数量。
- **读取规则**：
  - `w:del` 中的文字不读；
  - `moveFrom` 不读，`moveTo` 读；
  - 段落标记删除意味着与下一段合并；
  - 修订删除的表格行整行去掉；
  - 格式修订直接取当前值。
- **遇到无法识别的修订**（例如单元格级插入或删除、表格属性修订、编号修订）：
  - 建议**明确提示**哪类修订、出现在哪里。
  - 是否继续比较，由用户决定，不能静默忽略。
- **批注锚在被删除的修订文字上**：接受删除后锚点为空。按 §3.8 处理，保留批注并移动锚点。

### 3.12 会话与状态

- **交换左右文件**会使所有选择失效。有选择记录时交换，需先确认并清空选择。
- **重新上传其中一份**也会使选择失效。
- **长文档审阅可能跨越几天。** 建议提供“保存审阅进度”：导出一个小 JSON 文件，记录两份文件的指纹和每处选择。下次上传同样两份文件时，可以恢复进度。
  - 浏览器本地存储不可靠，可能被清空，不宜作为唯一手段。
  - 首版做不做，需要决定。【待定】
- **意外关闭页面**：有未导出的选择时，离开页面前提示。

### 3.13 导出

- **导出方式**：以“接受全部修订后的新版 XML”为底稿，只对选了旧版的片段做定点修改。
- **一致性检查**：如果所有片段都是新版，导出内容应与“接受修订后的新版”一致。这条可以作为自动化测试的硬约束（对应验收 7）。
- **为 Track Changes 导出预留结构**：
  - 后续的 Track Changes 导出，只是把同一份修改计划写成 `w:ins`/`w:del`，而不是直接替换。
  - 因此首版的数据结构要保留：每处修改的位置、新版原文字、写入的旧版文字。
  - 这样以后加 Track Changes 时不用重写比较和合并。
- **导出后自检**：在浏览器内用自己的解析器重新读取导出文件，确认能解析，且内容与“最终结果预览”一致。不一致时给出警告。
