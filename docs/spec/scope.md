# 目标、范围与部署

> 现行规则。改动时直接改本文件，并在 [../decisions.md](../decisions.md) 记一条决定。
> 支持哪些文件见 [reading.md](reading.md) §1；每种 Word 元素的逐项状态见 [comparison.md](comparison.md) §8。

## 1. 产品目标

做一个在公司 Windows 浏览器中使用、无需安装客户端的 Word 文档对比与合并工具。

用户可以像阅读 VS Code 的左右 diff 一样，查看旧版与新版的对应内容和差异。对每一处差异，选择采用旧版还是新版，最后导出合并后的 Word 文件。

当前范围是英文 Word 文档的**内容**比较，包括正文、标题、列表和表格。格式比较以后单独做（决定 47）；Excel 以后再做。开发路线见 [../overview.md](../overview.md) §2。

## 2. 已确认需求与设计理由

| 需求 | 具体约定 | 为什么这样做 | 详见 |
|---|---|---|---|
| 使用环境 | 公司 Windows 浏览器；无需安装客户端 | 方便在工作环境中使用，减少安装与分发负担 | §3 |
| 界面语言 | 英文 | 同事都是美国人 | |
| 使用方式 | 个人使用；不设计多人协作或审阅交接 | 先满足个人审阅场景 | |
| 文档规模 | 十几页到 200 页以上；目前没有处理时间要求，但长文档需显示处理进度、界面不卡顿 | 覆盖实际文档范围 | |
| 部署形态 | 文件只在用户浏览器本地处理，不上传服务器；可发布到 Posit Connect，也可作为单个 HTML 文件离线使用 | 文件不离开本机，合规风险最小；同一套产物两种用法 | §3 |
| Word 优先 | 先支持英文 .docx，包含表格；.doc 不读取，提示用户在 Word 中另存为 .docx 后上传；Excel 后续开发 | 聚焦主要使用场景，先保证一种文档的比较与合并可靠；.doc 只偶尔出现（多为旧版），Word 自己转换比自研解析更准确 | [reading.md](reading.md) §1、决定 33 |
| 左右对比 | 左边旧版，右边新版；对应内容对齐 | 直观看清修改前后内容，减少来回查找 | [ui.md](ui.md) |
| 统一阅读样式 | 两边使用同一套网页字体、字号和颜色，不沿用原文件的字体设置；标题层级、列表、表格等结构按各自原文显示，结构不同时两边看起来会不同（例如旧版 Heading 1、新版 Heading 2，左边显示为一级标题，右边显示为二级标题） | 保持可读性，同时减少原始格式差异对内容审阅的干扰 | [ui.md](ui.md) §1 |
| 内容与格式分开 | 分别检查、分别呈现；格式检查暂缓（决定 47），以后内容、格式各出一套结果，用户可以只看其中一种，也可以同时显示 | 避免字体、间距等变化淹没内容修改 | [comparison.md](comparison.md) §1、§9 |
| 已有修订 | 两份上传文档均按接受全部已有 Track Changes 后的状态参与比较 | 为每份文件取得明确的内容状态 | [reading.md](reading.md) |
| 原文件不变 | 在内部工作副本上处理，不修改上传的原文件 | 保留原始文件及其历史 | |
| 合并方式 | 每处差异选择“采用旧版”或“采用新版”，默认新版；任何选择组合都有效 | 与 VS Code diff 的使用习惯一致，选择之间不会互相冲突 | [merge.md](merge.md) |
| 导出底稿 | 以接受已有修订后的新版文件为底稿，只修改选择了旧版的位置 | 尽量保留新版的样式、结构和其他文档元素 | [export.md](export.md) |
| Clean 导出 | 优先开发；输出合并后的 Word，无未决修订 | 首先完成实际可用的工作闭环 | [export.md](export.md) |
| Track Changes 导出 | 暂缓（决定 39）；记录“新版 → 最终版”的变化；导出的修改计划已为此预留 | 让接收者查看本次审阅对新版做了哪些调整 | [export.md](export.md) §3 |
| 导出样式 | 保留新版原有样式体系；不将网页统一样式写回 Word | 网页用于清楚阅读，Word 保持正式文档样式 | [export.md](export.md) |
| 批注 | 逐条比较，只提示；Clean 保留新版已有批注，不汇入旧版批注；内容视图中显示两版批注的位置标记 | 聚焦主体内容；选择前就能知道哪里挂着批注 | 决定 8、19、46 |
| 未比较可见 | 不支持比较的元素必须在界面上可见，并标为“未比较” | “未比较”不能被误读为“无差异” | [comparison.md](comparison.md) §5 |
| 工具内编辑文字 | 不支持；需要第三种写法时，导出后在 Word 中修改 | 聚焦二选一 | 决定 13 |
| 非“旧→新”场景 | 暂不支持（如两家供应商的合同对比），沿用 old / new 模型 | 先把“旧→新”做好 | 决定 20 |

## 3. 部署形态与技术方向

### 3.1 部署形态

- 所有解析、比较、合并、导出都在浏览器本地完成，文件不上传。
- 同一份构建产物有两种用法：
  - 作为静态网页发布到公司 Posit Connect；
  - 作为单个 `.html` 文件分发，离线双击使用。
- 页面显示版本号。以 Posit Connect 上的版本为准，离线副本需自行替换为最新版本。
- 不依赖大模型做基础差异检测。

为什么选纯浏览器端而不是服务器端，当时的对比分析见 [../archive/design-review-v0.1.md](../archive/design-review-v0.1.md) §1。

### 3.2 技术方向

- TypeScript + Vite + React。
- JSZip 读写 .docx；浏览器原生 `DOMParser`／`XMLSerializer` 操作 XML（决定 22）。
- 导出时只改动选了旧版的地方；没涉及的部分（样式、图片、页眉页脚等）从新版原样复制，不重新生成。例外：新版中未接受的修订会在导出时被接受。
- 段落与表格行对齐使用自研算法：先按规范化文本序列对齐，再在变化区间内按相似度配对，处理改写、拆段、合段与移动。
  - 为什么自研：通用 diff 库只判断两段“完全相同”或“不同”。一段只改一个词，会被当成整段删除加整段新增；拆段、合段、移动、表格内单元格的修改也都识别不了。商业的 Word 比较组件要么需要服务器，要么体积大、需要授权，与“本地处理、可离线使用单个 HTML 文件”冲突。
  - 自研的范围：底层序列比较用公开、成熟的 Myers 算法（与 git diff 同一原理），自己实现一份，段落对齐和词级高亮共用；真正自研的是其上的配对逻辑。效果由 `testdocs/` 的样例及预期结果验证。
- XML 解析和写回在主线程（`DOMParser` 不能在 Worker 中使用），对齐和比较在 Web Worker 中运行；长文档使用虚拟滚动；不使用 Monaco。
- 单文件构建，以支持离线使用。
- 自动化测试以 `testdocs/` 为黄金样例。

技术细节由开发方决定（决定 23），见 [../implementation/](../implementation/)。

### 3.3 需要在公司环境确认

- 公司 Edge／Chrome 能否从本地打开含脚本的 HTML 文件。
- 浏览器是否允许页面启动后台线程（Web Worker）。不允许时工具会自动退回普通方式运行，结果相同，只是很长的文档比较时界面可能短暂停顿。
- 通过邮件或 Teams 收到的 HTML 文件是否被拦截。

## 4. 范围

### 4.1 已完成的范围：Word 内容比较与合并

开发顺序和版本见 [../overview.md](../overview.md) §2.1。

**比较**

- 正文和标题文字的新增、删除、修改，英文词级高亮。
- 段落及表格的对齐，包括改写、拆段、合段；移动内容的识别。
- 列表文字和条目增删；自动编号本身不算内容差异，编号不同时只以 “№” 提示（[comparison.md](comparison.md) §6，决定 38）。
- 表格单元格文字修改、表格行增删；列和合并单元格的结构变化识别为“表格结构变化”，整表选择。
- 上标、下标作为内容参与比较；隐藏文字显示（虚线标注）并参与比较。
- 页眉页脚、脚注尾注、文本框、超链接地址、图片、文档属性、批注：在 Other parts 中逐项对比，只提示（决定 45、46）。

**选择**

- 每处差异采用旧版或新版，默认新版；一对一修改的段落可以逐处选择（决定 42）。
- 撤销、重做、批量操作；进度文件和浏览器自动保存。
- 含脚注、超链接、域、图片、公式的旧内容也可以采用旧版（决定 43）。

**导出**

- Clean .docx：以新版为底稿，只改选了旧版的地方；结构保护；导出后自检。

### 4.2 以后的范围

- 格式比较（决定 47）：内容比较、格式比较各出一套结果，可只看其一或同时显示。
- Track Changes 导出（暂缓，决定 39）。
- 页眉页脚、脚注文字、批注等现在只提示；以后如有需要，再逐项做成可以采用旧版的差异。
- 图表、形状、SmartArt、文本框、嵌入对象的比较和带回。
- Excel 对比，单独设计工作表、单元格和记录匹配逻辑。

## 5. 验收标准

逐条的完成状态和对应测试见 [../overview.md](../overview.md) §5.1。

1. 仅发生样式变化、文字未变时，内容比较不产生虚假的文字修改。
2. 同一段落因 run 拆分（run 的含义见 [comparison.md](comparison.md) §1）、换行或分页不同，不被误判为内容变化。
3. 新增一个段落后，后续相同内容仍能合理对齐。
4. 英文句子中仅一个词或数字变化时，能够清楚高亮实际修改；上下标中的变化同样能识别。
5. 表格保持表格呈现，能够识别单元格修改和行增删；结构变化时提供整表选择。
6. 上传文件已有修订时，比较结果基于接受全部修订后的内容。
7. 默认最终结果等于处理已有修订后的新版；全部采用新版时，导出内容与接受修订后的新版一致。
8. 选择与撤销仅改变选定片段。
9. 移动内容合成一个差异，任何选择都不产生重复或丢失。
10. 自动编号的顺延不被判为内容变化（只提示，不产生差异）。
11. 采用旧版不破坏分节、页面设置、书签和批注结构；撤回含分节符的新增段落后，其余部分页面设置不变。
12. Clean 导出没有未决修订，保留新版已有批注与基础样式，并能被 Word 正常打开。
13. 后续 Track Changes 导出仅反映新版到最终版的差异。
14. 原始上传文件不变。
15. 未支持或未检查的内容有明确说明和占位，不被显示为“无差异”。
16. 审阅进度可保存并在同样两份文件上恢复。

## 6. 发布前验证

自动测试用 `testdocs/` 的 18 对样例覆盖了对齐、表格、修订、导出等情况。还需要在公司环境中手工验证（Windows Word 打开导出文件、公司浏览器、Posit Connect、真实文档），都通过后发布 v1.0.0（决定 48）。步骤见 [../dev guidance/release-checklist.md](../dev%20guidance/release-checklist.md)。
